### P-1: Route file structure

**Source:** [`server/src/routes/goals.ts:13-149`](../../../server/src/routes/goals.ts).

```typescript
import { Router } from "express";
import type { Db } from "@armyofagents/db";
import { createGoalSchema, updateGoalSchema } from "@armyofagents/shared";
import { validate } from "../middleware/validate.js";
import { goalService } from "../services/index.js";
import { HttpError, badRequest, notFound } from "../errors.js";
import { assertCompanyAccess } from "./authz.js";
import { assertRole } from "../middleware/rbac.js";

export function goalRoutes(db: Db) {
  const router = Router();
  const svc = goalService(db);

  router.get("/companies/:companyId/goals", async (req, res) => {
    const companyId = req.params.companyId as string;
    assertCompanyAccess(req, companyId);
    const result = await svc.list(companyId);
    res.json(result);
  });

  router.post("/companies/:companyId/goals", validate(createGoalSchema), async (req, res) => {
    const companyId = req.params.companyId as string;
    assertCompanyAccess(req, companyId);
    await assertRole(db, req, companyId, "founder", "team_lead");
    const result = await svc.create(companyId, req.body);
    res.status(201).json(result);
  });

  router.get("/goals/:id", async (req, res) => {
    const id = req.params.id as string;
    const goal = await svc.getById(id);
    if (!goal) {
      res.status(404).json({ error: "Goal not found" });
      return;
    }
    assertCompanyAccess(req, goal.companyId);
    res.json(goal);
  });

  return router;
}
```

**Mounted in `server/src/app.ts:186`:**
```typescript
api.use(goalRoutes(db));   // teamRoutes(db) goes alongside this
```

**Properties:**
- Factory function `xRoutes(db: Db)` returns the Router.
- Full paths used in route handlers (no separate `mergeParams` Router with prefix mount).
- `assertCompanyAccess(req, companyId)` validates the caller can access this company.
- `assertRole(db, req, companyId, ...)` validates RBAC for write operations.
- `validate(schema)` middleware Zod-parses the body into `req.body`.
- Errors are **thrown** (`throw notFound("...")`); global error middleware converts to JSON.
- 201 status on POST create; 200 default for others; 404 explicit for not-found.

### P-2: Error handling — no try/catch in routes

**Source:** [`server/src/middleware/error-handler.ts:1-55`](../../../server/src/middleware/error-handler.ts) and [`server/src/errors.ts`](../../../server/src/errors.ts).

```typescript
// errors.ts exports
export function badRequest(message: string, details?: unknown): HttpError;
export function unauthorized(message?: string): HttpError;
export function forbidden(message?: string): HttpError;
export function notFound(message?: string): HttpError;
export function conflict(message?: string): HttpError;
export function unprocessable(message?: string, details?: unknown): HttpError;

// HttpError extends Error and carries .status + .details

// Global middleware (mounted at app.ts:350 — last middleware)
export function errorHandler(err, req, res, _next) {
  if (err instanceof HttpError) {
    res.status(err.status).json({ error: err.message, ...(err.details ? { details: err.details } : {}) });
    return;
  }
  if (err instanceof ZodError) {
    res.status(400).json({ error: "Validation error", details: err.errors });
    return;
  }
  res.status(500).json({ error: "Internal server error" });
}
```

**Properties:**
- Routes never use try/catch around their happy path. They `throw badRequest(...)`, `throw notFound(...)`, etc.
- ZodError from `validate(...)` middleware is caught here automatically.
- Status code conventions:
  - **201** = create success
  - **400** = ZodError (validation)
  - **401** = unauthorized (no auth)
  - **403** = forbidden (auth exists, denied)
  - **404** = not found
  - **409** = conflict
  - **422** = unprocessable (FK or business logic error)

### P-3: UI API client

**Source:** [`ui/src/api/client.ts:60-71`](../../../ui/src/api/client.ts).

```typescript
export const api = {
  get: <T>(path: string) => request<T>(path),
  post: <T>(path: string, body: unknown) =>
    request<T>(path, { method: "POST", body: JSON.stringify(body) }),
  postForm: <T>(path: string, body: FormData) =>
    request<T>(path, { method: "POST", body }),
  patch: <T>(path: string, body: unknown) =>
    request<T>(path, { method: "PATCH", body: JSON.stringify(body) }),
  put: <T>(path: string, body: unknown) =>
    request<T>(path, { method: "PUT", body: JSON.stringify(body) }),
  delete: <T>(path: string) => request<T>(path, { method: "DELETE" }),
};
```

**Usage example from [`ui/src/api/agents.ts:56-99`](../../../ui/src/api/agents.ts):**

```typescript
export const agentsApi = {
  list: (companyId: string) => api.get<Agent[]>(`/companies/${companyId}/agents`),
  create: (companyId: string, data: Record<string, unknown>) =>
    api.post<Agent>(`/companies/${companyId}/agents`, data),

```

**Properties:**
- `api.get<T>(path)` returns `Promise<T>` directly (response is parsed JSON).
- POST/PATCH/PUT take body as 2nd arg (already serialized internally).
- `postForm<T>` for multipart uploads (used by file imports).
- `credentials: "include"` is set in `request()` so auth cookies travel.
- Error responses throw `ApiError` automatically.

### P-5: RBAC

**Source:** [`server/src/routes/authz.ts:10-26`](../../../server/src/routes/authz.ts) and [`server/src/middleware/rbac.ts:24-53`](../../../server/src/middleware/rbac.ts).

```typescript

// Imported from "../middleware/rbac.js" in route files
export async function assertRole(
  db: Db,
  req: Request,
  companyId: string,
  ...roles: UserRole[]   // "founder" | "team_lead" | "team_member"
): Promise<void>;
```

**Usage pattern in route handlers:**
```typescript
router.post("/companies/:companyId/teams", validate(createTeamSchema), async (req, res) => {
  const companyId = req.params.companyId as string;
  assertCompanyAccess(req, companyId);                                        // throws unauthorized/forbidden
  await assertRole(db, req, companyId, "founder", "team_lead");                // throws forbidden if neither
  // ... happy path
});
```

**Properties:**
- `assertCompanyAccess` throws `HttpError` (401 or 403) on fail.
- `assertRole` is async (queries `userRoles` to resolve effective role); takes variadic role list (caller passes one of these is OK).
- Agent actors (machine callers via Bearer token) bypass `assertRole` (they have their own access scoping via `agent.companyId`).
- `local_trusted` mode bypasses everything.

### P-7: Heartbeat prompt construction — the actual injection point

**Source:** [`server/src/services/context-packaging.ts:22-101`](../../../server/src/services/context-packaging.ts).

The function is **`contextPackagingService(db).assembleContext(companyId, issueId)`** returning `{ markdown, tokenEstimate }`. Sections (in order):
1. Company identity (vision/mission/values + identity-layer memory)
2. Department/project (with domain-layer memory scoped to the department)
3. Goal + active_context-layer memory
4. Task dependencies (incl. their artifacts)
5. Task details
6. Artifacts attached to the task
7. Agent config + per-agent context mode
8. Founder preferences

This single function is the ONE injection point for heartbeat agent runs — the resulting markdown is what gets passed to the adapter (via `--append-system-prompt-file` for claude-local).

**Implication for Slice 6:** instead of writing a separate `appendTeamCoordination(db, agentId, basePrompt)` helper as my plan said, the correction is to **extend `assembleContext()` itself with a new section for team coordination**. The team coordination doc should be added as a section in `context-packaging.ts` between sections 7 (agent config) and 8 (preferences) — call it section 7.5 "Team Coordination."

`runtimeConfig.contextMode` already controls section sizes and which sections to include — extend the `sectionLimits` map accordingly.

## Part 4 — Heartbeat Injection Re-design (the biggest correction)

### What the original plan said (Slice 6)

Three tasks creating a new `appendTeamCoordination(db, agentId, basePrompt)` helper, called from heartbeat.ts after the existing system-prompt build.

### Why that was wrong

1. There's no single "after the existing system-prompt build" hook in the current architecture — the prompt is assembled by `contextPackagingService.assembleContext()` which already returns markdown.
2. Calling `appendTeamCoordination` separately means duplicating the `agents.runtimeConfig.contextMode` lookup that `assembleContext` already does.
3. The team coordination data is conceptually a section of the agent's context, not a separate thing — putting it in `assembleContext` matches the existing pattern.

### Re-designed Slice 6 (replaces existing Tasks 6.1–6.3)

**New structure: extend `contextPackagingService.assembleContext()` directly.**

#### Task 6.1 (NEW): Add team-coordination fetch to context-packaging service
