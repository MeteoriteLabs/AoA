## Failures

**F-1 — `P1-RESOLVER-EXACT` and the operator posture in `P1-OPERATOR-UNCHANGED` do not hold at
`Revision`.** Class `product`: the product at this revision lacks the certified property. **This is
not a regression.** JOB-002 (`0221`) and JOB-009 (`0224`) deliberately widened the grants, and the
exact startup certificate `PLAN_DERIVED_ACL_MATRIX` records that widening. The first causal fact
is the `0221` statement
`GRANT SELECT ("id", "organization_id", "owner_user_id", … "capabilities") ON "execution_targets" TO "aoa_app"`.
So the P1 gate, as `a5` worded it, is a **revision-scoped** claim. It cannot be re-certified at a
later tree, and fresh evidence on a later tree cannot stand in for it. **A `pass` here would turn a
superseded posture into a current one.** H-10 forbids that.

**F-2 (observation, harness) — the P1 integration suite certifies a database state that production
never has.** `e2-serving-role-correction.integration.test.ts` `beforeAll` runs
`applyPendingMigrations` and then re-applies `0214` + `0215` twice. `0214` contains
`REVOKE ALL PRIVILEGES ON ALL TABLES IN SCHEMA public FROM "aoa_app"` (and the same for
`aoa_operator`) and re-grants the E2-era matrix. After that, the suite's authority assertions (four
denied resolver columns, operator writes rejected) describe the E2-era grant set, not the grants of
the tree under test. **A green count from this file is therefore not evidence of the tree's
production grants.** No finding is minted here. The gate owner decides whether this becomes one.

**Neither failure touches H-01.** Row visibility on `execution_targets` is still owned by the forced
policies, and the wider grants are column privileges inside them.
