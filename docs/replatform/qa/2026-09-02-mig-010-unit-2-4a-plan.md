# MIG-010 Unit 2.4a — the watermark exists and is written, before anything reads it

> **For agentic workers:** implement task-by-task, in order. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Make the reconciliation pass record a durable, DB-clock **snapshot instant** it can later be
gated on — and make lease `created_at` comparable to it. Nothing reads the marker yet.

**Design authority:** [`2026-09-01-blocker-e-2-e-3-design.md`](./2026-09-01-blocker-e-2-e-3-design.md).

`lease_ids[]`/`unnarrowed_total` contract, `reconciliation_stale`, the freshness comparison, any
change to `canary-preflight.ts`. All of that is **2.4b**, and it is deliberately split off so the
gate changes land against a marker that already exists and already has real rows.

**The canary stays shut.** Say so in the PR.

## Why this plan opens with probes

Three design rounds have now produced a mechanism that looked correct, passed review, and was wrong:
a company-scoped pass that could not call an org-bound function; an optional watermark that *opens*
the gate; a total that vanishes exactly when it is needed. **All three passed review. All three were
caught only by running PostgreSQL.**

So Task 1 measures, and every later task cites a probe result rather than an expectation. If a probe
disagrees with this plan, **the probe wins** — stop and report rather than reconciling the code to
the document.

## Task 1: Probes — measure before building

**Files:** Create `server/src/__tests__/mig-010-unit-2-4-probes.integration.test.ts`

These are throwaway-shaped but permanent: they pin PostgreSQL behaviours the design depends on, so a
future reader does not have to re-derive them. Use the `startMigratedDatabase` harness and its
`admin` client; create scratch functions in a temp schema, not `public`.

- [ ] **Step 1: The one-row contract (§11.1)**

Prove both halves in one test: a `RETURNS TABLE (ids uuid[], total bigint)` built from
`array_agg` + `count` returns **exactly one row even when the narrowed set is empty**, while the
`RETURNS TABLE (id uuid, total bigint)` shape returns **zero rows** in that case.

```ts
it("[§11.1] a set-returning shape loses the total on the empty set; the one-row contract keeps it", async () => {
  // …create both shapes over the same fixture, call each with a watermark that predates every row…
  expect(setShapeRows).toHaveLength(0);            // the total is UNOBSERVABLE — the §10.3 defect
  expect(oneRowShape).toHaveLength(1);
  expect(oneRowShape[0]).toMatchObject({ ids: null, total: 3n });  // or String(total), driver-dependent
});
```

★ Record in the test what the driver actually returns for `bigint` (`bigint` vs string) — 2.4b's
comparison depends on it and getting it wrong is a silent `"3" > 0` bug.

- [ ] **Step 2: The overload trap (§11.2) — the fail-open, measured**

With a 2-arg function AND a 3-arg overload whose third parameter is **required**, a 2-arg call must
resolve **silently to the 2-arg function** (no 42725). Assert that, then assert that after
`DROP FUNCTION …(uuid, uuid)` the same call raises **42883**, not 42501.

★ This is the test that justifies the DROP in 2.4b. Without it the reason on record is wrong.

- [ ] **Step 3: Return-type immutability**

`CREATE OR REPLACE` changing only the `RETURNS TABLE` shape must raise **42P13**. This is why 2.4b
cannot avoid a DROP even at unchanged arity.

- [ ] **Step 4: `identity_arguments` rendering**

A `timestamptz` parameter must render as `timestamp with time zone`. Assert the exact string — the
manifest compares with exact equality and a `timestamptz` entry is a fatal every-boot failure.

- [ ] **Step 5: Clock semantics**

Prove `now()` is transaction-start and `clock_timestamp()` is not, inside one transaction. Then prove
the direction that matters: a row inserted by a transaction that **began before** a watermark read
carries `created_at < watermark` even when it **commits after** — i.e. it stays IN scope, which is
the fail-closed direction.

- [ ] **Step 6: Run, then commit**

```bash
cd /c/e3 && AOA_RUN_WIN_INTEGRATION=1 npx vitest run server/src/__tests__/mig-010-unit-2-4-probes.integration.test.ts
```

## Task 4: The pass writes the marker — and aborts on a rotation

**Files:** `server/src/services/legacy-resource-reconciliation.ts` + its store + the CLI.

- [ ] **Step 1:** Read the snapshot instant from the **database** before listing anything, and thread
  it through the pass.

- [ ] **Step 2 ★★★: The rotation abort (§11.3, BLOCKING) — and it must be TRANSACTIONAL**

If the provider key rotates mid-pass, records land under two generations, the gate refuses on any
superseded record (`canary-preflight.ts:157-171`), and the pass currently reports success — a
permanently ungateable company.

★ **An earlier revision of this plan said: re-read the generation before writing the marker, and if
it moved, write no marker. THAT IS INSUFFICIENT, and it was measured against the schema rather than
assumed.** Three facts kill it:

1. The poisoned records are **already on disk** before the re-read. Declining the marker does not
   undo them — it only declines to advertise them.
2. The gate refuses on any superseded record regardless of whether a marker exists, so the company
   is bricked either way.
3. **A retry cannot repair it.** The crosswalk's unique index is on `(company_id, resource_key)`
   (`legacy_resource_reconciliation.ts:73-76`) and `insertRecordIfAbsent` uses
   `onConflictDoNothing` (`legacy-resource-reconciliation-store.ts:89-91`), so re-running under the
   new generation inserts **nothing** — the old-generation rows survive permanently.

**What is actually sufficient: one transaction PER COMPANY, with the generation re-read inside it
immediately before commit.** If the generation moved, **ROLL BACK** — no records for that company
reach disk at all — and the retry is clean. Per-company rather than per-organization because closure
is asserted per company (`canary-preflight.ts:139-190`), and because it bounds transaction size on a
large org; a rotation *between* companies then leaves each individually consistent.

★ **There is no transaction seam today.** `legacy-resource-reconciliation.ts`,
`legacy-resource-reconciliation-store.ts` and `reconcile-legacy-resources.ts` contain no
`transaction` call — verify this yourself before designing around it. Adding one is part of this
step, and the store contract changes shape: records for one company must be written under a
caller-supplied transaction, not autocommitted one at a time.

★ **Test it, and test the repair.** Run a pass, rotate the generation mid-flight, then assert all
three: (a) **zero** records exist for that company — not merely no marker; (b) the CLI exits
non-zero saying why; (c) **a re-run afterwards succeeds and every record carries the NEW generation.**
(c) is the assertion that proves the state was retryable rather than poisoned, and it is the one the
insufficient remedy would have failed.

- [ ] **Step 3:** Marker write is the pass's **last** action, after every record. Nothing may
  observe a completed marker for a pass whose records are not all on disk.

- [ ] **Step 4:** Assert the pass is re-runnable after an abort and converges on the same records
  (append-only insert-if-absent).

- [ ] **Step 5:** Commit.
